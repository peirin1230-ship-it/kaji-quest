# kaji-quest 仕様書 v2.1

**自分ひとりが**家事・育児を継続するための GitHub リポジトリ仕様。
妻は管理対象ではない。システムの利用者は自分だけ。

---

## 1. 目的とゴール

### 1.1 背景
- 保育園の送り迎えは妻がメインで担っている。
- 自分が家事・育児を最大限引き受けることで、実質的な負担を同等に近づけたい。
- ただし「気合い」では続かない。**仕組みで自分を走らせる**のが本システムの役割。

### 1.2 このシステムが解くこと
| # | 課題 | 解 |
|---|------|-----|
| P1 | 何をやるべきか毎回考えるのが面倒 | Routine から自動でタスクを生成 |
| P2 | 忘れる／後回しにする | 時間帯別リマインド |
| P3 | やり方がわからず調べる手間で止まる | タスクにコツを自動添付 |
| P4 | 続いているのか実感がない | 換算時間・ストリーク・レベルで可視化 |
| P5 | 目標が曖昧で「やった気」になる | 週次の目標換算時間を数値で設定 |
| P6 | 知識が溜まらない | 気づきの蓄積＋間隔反復 |

### 1.3 ゴール
| # | ゴール | 測り方 |
|---|--------|--------|
| G1 | 自分が設定した週次目標を安定して達成する | 週次目標達成率 80% 以上 |
| G2 | 継続する | 12週連続で週次振り返りを実施 |
| G3 | 楽しい | 自分の mood 平均 3.5 以上 |
| G4 | 知識が身につく | スキルツリーが四半期ごとに1段階上がる |
| G5 | 忘れない | デイリータスク実施率 85% 以上 |

### 1.4 非ゴール（明確にやらないこと）
- **妻のタスクを登録・記録・集計しない。** 妻は本システムに一切登場しない。
- 妻に GitHub を使わせない。通知先にもしない。ダッシュボードを見せる義務もない。
- 夫婦の負担を数値で比較して突き合わせない。**数字は自分を走らせるためだけに使う。**
- 完璧な家事記録データベースを作らない。記録漏れは前提。

> 「負担を同等にする」は**動機**であって、システムの機能ではない。
> システムは自分の目標達成だけを追う（§6）。

## 2. 設計思想（6原則）

1. **これは自分ひとりのための道具である**
   相手を測る機能を一切持たない。関係性の問題を数字に持ち込まない。
2. **管理コストが新たな家事になってはいけない**
   1タスクの完了操作は15秒以内。迷ったら機能を削る。
3. **計測とゲームを分離する**
   目標管理は「換算時間」（真面目な数字）。XP・バッジ・ストリークはモチベーション用の別レイヤー。
4. **未達を責めない**
   追撃リマインドをしない。パス権と省エネモードを制度として持つ。
5. **見えない家事を見えるようにする**
   「名もなき家事」と「段取り・判断（メンタルロード）」を明示的に計上する。
6. **小さく始めて育てる**
   Phase 0 は Issue テンプレートだけ。自動化は動き出してから足す（§16）。

## 5. ドメインモデル

```
Routine（定期タスク定義） ──生成──> Task Issue ──完了──> LogEntry
       │                                │
       └── tips: Knowledge[]            └── learned: 気づき1行 → Knowledge Inbox

Knowledge（コツ）── 間隔反復 ──> Task Issue へ自動添付
SkillTree ── 達成条件 ──> LogEntry を集計して判定
WeeklyTarget ── 比較 ──> LogEntry 週次集計
```

### 5.1 Routine（定期タスク定義）

`routines/*.yml`。**ここがシステムの心臓部**。コード変更なしに追加できること。

```yaml
# routines/daily.yml
- id: dishes-night
  title: 夜の洗い物リセット
  area: dishes
  schedule:
    type: cron
    expr: "0 21 * * *"   # JST表記（Actions側でUTC変換）
  est_minutes: 15
  load:
    physical: 2          # 1-3
    mental: 1            # 1-3（段取り・判断の重さ）
    time_bound: 1        # 0-2（時間帯の縛り・中断不可性）
  core: true             # ★絶対防衛ライン（省エネモードでも残す）
  checklist:
    - 食器を洗う／食洗機を回す
    - シンクの水気を拭く
    - 排水口カゴを洗う
    - 三角コーナーのゴミを捨てる
  tips: [dishes-001, dishes-004]
  pass_allowed: true
```

```yaml
# routines/weekly.yml
- id: bathroom-deep
  title: 浴室の防カビ＆排水口
  area: cleaning
  schedule: { type: weekly, day: SAT, time: "10:00" }
  est_minutes: 30
  load: { physical: 3, mental: 1, time_bound: 0 }
  core: false
  checklist:
    - 排水口の髪の毛・ぬめり除去
    - 壁・床をこすり洗い
    - 50℃シャワーを全面に30秒
    - 防カビくん煙剤（月1・在庫確認）
  tips: [cleaning-012, cleaning-013]
```

```yaml
# routines/childcare.yml
- id: work-block
  title: 作業ブロック（子ども担当）
  area: childcare
  schedule: { type: manual }   # 妻が作業を始めるタイミングで自分が起票
  est_minutes: 60              # 実績で上書き
  load: { physical: 2, mental: 2, time_bound: 2 }
  attach: play_card            # 遊びネタカードをランダム添付
  core: true
  checklist:
    - 何時までかを確認する
    - 作業部屋のドアを閉める／呼びに行かせない
    - 終わったら子の様子を1行記録
```

> 起票は自分が `/block 60` とコメントするだけ、または Issue テンプレートから1タップ。
> **妻に何か操作させる設計にはしない。**

## 6. 週次目標の設定（負担同等の表現方法）

妻を測らずに「同等」を目指すため、**一度だけ自分で見積もって目標値に変換し、以後は自分の数字だけを追う**。

### 6.1 換算時間の定義

```
負荷係数 W = 1.0 + p + m + t

  p = 身体的きつさ      : physical 1→0.0 / 2→0.1 / 3→0.2
  m = メンタルロード    : mental   1→0.0 / 2→0.15 / 3→0.3
  t = 時間拘束・中断不可: time_bound 0→0.0 / 1→0.1 / 2→0.2

  W の範囲: 1.0 〜 1.7
  換算時間 = 実所要時間(分) × W
```

W を使う理由は2つ。
1. **中断できない育児**や**段取りの重い料理**を正当に評価するため。
2. **楽なタスクだけ選んで数字を稼ぐのを防ぐため**（実時間だけだと「楽な30分」で達成できてしまう）。

| タスク | 実時間 | p | m | t | W | 換算 |
|--------|--------|---|---|---|---|------|
| 夜の洗い物 | 15分 | 2 | 1 | 1 | 1.20 | 18分 |
| 翌日分の作り置き | 45分 | 2 | 3 | 1 | 1.50 | 68分 |
| 浴室の防カビ | 30分 | 3 | 1 | 0 | 1.20 | 36分 |
| 作業ブロック | 60分 | 2 | 2 | 2 | 1.45 | 87分 |
| ゴミ出し（名もなき家事） | 5分 | 1 | 2 | 2 | 1.35 | 7分 |

### 6.2 目標値の決め方（初回1回だけ・所要5分）

`docs/target.md` に、**自分の手元メモとして**書く。リポジトリにデータとして持たない。

```markdown
# 週次目標の根拠（2026-09 設定 / 次回見直し 2026-12）

## 妻の週あたり負担のざっくり見積もり（自分の主観・記録はしない）
- 送り 20分 × 5日、W=1.35 → 135分
- 迎え 25分 × 5日、W=1.35 → 169分
- 保育園の準備・連絡帳・持ち物 10分 × 5日、W=1.45 → 73分
- 寝かしつけ・食事介助など 平均40分 × 7日、W=1.45 → 406分
→ 合計 おおよそ 週 780 換算分

## 自分の週次目標
最終目標: 780 換算分/週
```

> この見積もりは**当てにいかなくていい**。桁が合っていれば十分。
> 精緻化しようとすると妻を観察・記録することになり、原則1に反する。

### 6.3 段階的な引き上げ（重要）

初週から満額を狙うと確実に折れる。4週ごとに上げる。

| 期間 | 目標比率 | 目標（例: 最終780分） |
|------|----------|----------------------|
| Week 1-4 | 50% | 390 換算分/週 |
| Week 5-8 | 70% | 546 換算分/週 |
| Week 9-12 | 85% | 663 換算分/週 |
| Week 13〜 | 100% | 780 換算分/週 |

`config.yml` の `target.ramp` に定義し、Bot が自動で現在の目標を算出する。
**2週連続で未達なら、比率を自動で1段階下げる**（無理な目標に追い立てられないため）。

### 6.4 運転モード

| モード | 内容 | 発動 |
|--------|------|------|
| **フル** | 全 Routine を生成。目標100% | 通常 |
| **省エネ** | `core: true` のみ生成。目標は40%に縮退 | `/mode eco 7d` で自分が宣言 |
| **休止** | 生成停止。ストリークは維持 | `/mode off 3d` |

省エネ・休止でストリークは切れない。**縮退は失敗ではなく設計された選択肢**。

### 6.5 妻との関わり方（システム外）
- 月に一度、雑談レベルで「最近どう？しんどいとこある？」と聞く。それだけ。
- 数字を見せて交渉材料にしない。見せたくなったら §17 のアンチパターンを読み返す。
- 本当の指標は、週報の数字ではなく**妻の表情と会話の温度**。それはログには残らない。

## 7. ゲーミフィケーション設計（ソロプレイ）

比較対象は**過去の自分だけ**。

| 要素 | 仕様 |
|------|------|
| **XP** | `XP = 換算時間(分)`。別計算にしない（点数稼ぎの余地をなくす） |
| **レベル** | 領域別に累計XPで決定。`Lv = floor(sqrt(累計XP / 100))`。掃除Lv3、料理Lv2 |
| **ストリーク** | 「1日1つ以上完了」の連続日数。週1の**フリーズ権**（パス）と省エネモードで途切れない |
| **自己ベスト** | 週次換算時間の最高記録、連続達成週数。更新したら週報で祝う |
| **先週比** | 週報に「先週比 +8%」を表示。絶対値より変化を見る |
| **バッジ** | **全120種以上**（§7.3）。`docs/badges.md` に YAML で定義し、Bot が自動判定 |
| **称号** | 獲得バッジ数で変化。5→見習い / 15→家事人 / 30→熟練 / 50→師範 / 80→家事の匠 / 120→伝説 |
| **週次クエスト** | Bot が月曜に1つ提示。「今週は換気扇に挑戦」「新しい副菜を1つ」。達成でボーナスXP |
| **ごほうび** | `config.yml` に自分で設定。週の目標達成でアンロック（例: 好きなだけゲーム、欲しかった調理器具の購入権） |

### 7.1 やらないこと
- ❌ 誰かとのランキング
- ❌ 未達時のXP減点・ペナルティ
- ❌ 高XPタスクだけ選べる設計（`core` は必須、選択制はウィークリーのみ）
- ❌ **バッジの剥奪**。一度取ったものは永久に残る

### 7.2 バッジの仕組み

#### 定義フォーマット（`docs/badges.md` に YAML ブロックで記述）

```yaml
- id: streak-030
  name: 一ヶ月の守護者
  icon: 🔥
  tier: gold               # bronze | silver | gold | platinum | secret
  desc: ストリーク30日達成
  condition: { type: streak, gte: 30 }
  xp_bonus: 100
  secret: false
```

**condition の type 一覧**

| type | 意味 | 例 |
|------|------|-----|
| `streak` | 連続日数 | `{ type: streak, gte: 30 }` |
| `count` | 完了回数（`area` / `task_id` で絞り込み可） | `{ type: count, task_id: dishes-night, gte: 100 }` |
| `weighted_total` | 累計換算時間（分） | `{ type: weighted_total, gte: 6000 }` |
| `target_hit` | 週次目標の達成回数／連続回数 | `{ type: target_hit, consecutive: 10 }` |
| `level` | スキルツリー到達 | `{ type: level, area: cooking, gte: 3 }` |
| `knowledge` | ナレッジ件数・コツ実践回数 | `{ type: knowledge, practiced_gte: 100 }` |
| `first` | そのタスクの初回完了 | `{ type: first, task_id: range-hood }` |
| `combo` | 複数バッジの同時保有 | `{ type: combo, all_of: [kitchen-hood, grill, burner] }` |
| `custom` | スクリプトで判定 | 「見込みの半分の時間で完了」など |

#### 獲得時の演出
1. `on-issue-closed.yml` が判定 → 該当 Issue に**祝いコメント**を投稿
2. 通知チャネルへプッシュ（**バッジ獲得だけは静穏時間を無視してよい設定**、既定は尊重）
3. `docs/badges.md` の該当行に獲得日を自動追記（`achieved: 2026-09-15`）
4. ボーナスXPを加算

#### 「あと少し」の可視化 ★継続効果が最も高い
朝ダイジェストと週報に、**達成率が高い未獲得バッジを上位3件**表示する。

```
🏅 あと少し
  🔥 一ヶ月の守護者   ████████░░  23/30日
  🍳 仕込み職人       ███████░░░  36/50回
  🧼 排水口の支配者    █████████░  9/10回
```

#### シークレットバッジ
条件を非公開にしたバッジ群（`secret: true`）。一覧では `???` と表示され、獲得時に初めて名前と条件が明かされる。**偶然の達成感**が継続のスパイスになる。獲得済みシークレットの数だけ `2/4` のように表示する。

### 7.4 バッジ設計の注意
- **前半を薄く刻む。** 最初の2週間で 8〜10 個取れる配分にする。ここで達成感がないと続かない。
- **上限を作らない。** 500回・一年などの遠い目標を必ず残しておく。
- **引き算のバッジ（Iカテゴリ）を必ず含める。** これがないと「増やすゲーム」になって破綻する。
- **バッジのために無理をしない。** 「深夜に完了」「連続◯時間」のような、健康や睡眠を削る条件は作らない。

## 8. リマインド設計

### 8.1 タイミング（JST）

| 時刻 | 種類 | 内容 |
|------|------|------|
| **05:00** | 朝ダイジェスト | 今日のタスク、今日のコツ1つ、今週の目標進捗（例: 210/390）、あと少しのバッジ |
| **17:00** | 帰宅前 | 今夜仕込む翌日メニュー、不足食材、所要時間の目安 |
| 21:00 | 夜のリセット | 洗い物・明日の準備、子の記録1行の促し |
| 日 21:00 | 週報 | 目標達成率、先週比、ストリーク、獲得バッジ、来週のクエスト |

> 朝 05:00 に配信するため、タスク生成は **04:30 JST** に前倒しする（§12.1）。
> 17:00 は退勤前後に届く想定。通勤中に「今夜これを作る」が頭に入っている状態を作るのが狙い。

### 8.2 ルール
- **静穏時間 22:00〜04:30 は通知しない。**
- **未完了への追撃通知をしない。** 翌朝のダイジェストに `carry-over` として静かに再掲されるだけ。
- 1日の通知は最大3回。増やしたくなったら他を削る。

### 8.3 通知チャネル
自分にしか届かないので、**GitHub Mobile のプッシュ通知で十分**（Issue の assignee/mention）。
追加設定を入れるなら Discord Webhook（無料・安定・5分で設定）。
LINE 連携は不要（妻に送らないため）。

### 8.4 cron の注意点
- GitHub Actions の cron は **UTC**（JST = UTC+9）。

| JST | cron (UTC) | 用途 |
|-----|-----------|------|
| 04:30 | `30 19 * * *`（前日） | タスク生成 |
| 05:00 | `0 20 * * *`（前日） | 朝ダイジェスト |
| 17:00 | `0 8 * * *` | 帰宅前 |
| 21:00 | `0 12 * * *` | 夜のリセット |
| 日 21:00 | `0 12 * * 0` | 週報 |

- スケジュール実行は高負荷時に**数十分遅延することがある**。分単位の正確さに依存しない設計にする。
- 特に **05:00 の朝ダイジェストは遅延すると出勤前に見られない**。生成を30分前倒ししてあるのはそのバッファ。それでも不安なら、朝の通知だけ iOS ショートカットの時報トリガーで GitHub API を叩く構成に置き換えられる（Phase 4）。
- 長期間リポジトリに活動がないと scheduled workflow が自動無効化されうる。毎日ログをコミットするため実質問題ないが、**長期の休止モード明けは Actions タブを確認**する。

### 9.2 コツの配信（US-03）
1. Task Issue 生成時、その Routine の `tips` からコツを1つ選び本文に埋め込む。
2. 選択は**間隔反復**: `next_review` を過ぎたものを優先。なければ未読を1つ。
3. Issue 内に「✅ 今日このコツを実践した」チェックボックス。
4. チェックされたら `practiced +1`、`interval_days` を **1 → 3 → 7 → 30 → 90** と伸ばす。実践されなければ間隔を戻す。

→ **忘れた頃に再提示され、定着したものは出てこなくなる。**

## 12. ワークフロー仕様

### 12.1 `generate-tasks.yml`
- **トリガー**: 毎日 **04:30 JST**（`30 19 * * *` UTC）＋ `workflow_dispatch`
- **制約**: 05:00 の朝ダイジェストより前に必ず完了していること。処理は1分未満で終わる想定。
- **処理**:
  1. `config.yml` の現在モードを判定（フル / 省エネ / 休止）
  2. `routines/*.yml` から当日対象を抽出（省エネなら `core: true` のみ）
  3. 同 `id`＋同日の Open Issue がなければ新規作成（**冪等**）
  4. 負荷係数 W を計算しラベル付与
  5. `tips` から間隔反復ロジックでコツを1つ選び本文に埋め込む
  6. `attach: play_card` があれば遊びネタカードを1枚添付
  7. Project の「今日」へ追加
  8. 前日の未クローズ Issue に `status/carry-over` を付与し日付を更新

### 12.2 `notify-*.yml`
- **トリガー**: 05:00 / 17:00 / 21:00 JST
- **処理**: Open Issue を集計して通知。静穏時間を尊重。
- **夕方は特別扱い**: `area/cooking` からレシピ・所要時間・不足食材を抽出してリッチに通知。

### 12.3 `on-issue-closed.yml`
- **トリガー**: `issues: [closed]`
- **処理**:
  1. 本文の実績欄（実時間・気分・気づき・コツ実践）をパース
  2. 実時間が未入力なら `est_minutes` を採用
  3. 換算時間・XP を計算し `logs/YYYY/MM.jsonl` へ追記（`[skip ci]` でコミット）
  4. 気づきがあれば `knowledge/_inbox.md` へ追記
  5. コツ実践チェックがあれば当該ナレッジの `review` を更新
  6. バッジ・レベルアップ判定 → 達成したら Issue にコメントで祝う 🎉

### 12.4 `slash-commands.yml`
- **トリガー**: `issue_comment: [created]`

| コマンド | 動作 |
|----------|------|
| `/done 25` | 実時間25分で完了。ログ追記してクローズ |
| `/done 25 mood:4 気づき本文` | 実績をまとめて記録 |
| `/pass` | パス権を消費してクローズ。ストリーク維持 |
| `/snooze 2d` | 2日後に再スケジュール |
| `/block 45` | 作業ブロックを実績45分で起票＆完了 |
| `/mode eco 7d` | 7日間の省エネモード |
| `/mode full` | 通常運転に復帰 |
| `/tip` | そのタスクのコツをもう1つ引く |
| `/skip-task <id>` | この Routine を今後生成しない（やめる家事） |

### 12.5 `weekly-report.yml`
- **トリガー**: 日曜 21:00 JST
- **処理**: 週次集計 → 振り返り Issue を自動作成 → 通知 → `docs/retrospectives/` に保存

**週報テンプレート**
```markdown
## 2026-W38 週次レポート
```

## 16. 継続の仕掛けとアンチパターン

### 16.1 続けるための仕掛け

| 仕掛け | 意図 |
|--------|------|
| 段階的な目標引き上げ | 初週満額は必ず折れる。成功体験から始める |
| 自動ダウンシフト | 未達が続いたら目標側が折れる。人は折れない |
| パス権（週1） | 「1日も休めない」設計は続かない。休みを制度化 |
| 省エネモード | 繁忙期に全部やめるか全部やるかの二択にしない |
| ストリークフリーズ | パス・省エネでストリークが切れない |
| 繰り越しの自動再掲 | 忘れても静かに戻るだけ。罪悪感を増やさない |
| `core` ラベル | 「最低これだけ」が明確なので、どんな週でも0にならない |
| 月次の「やめる家事」 | タスクは放置すると増える。削る儀式を制度化 |
| 気づき1行 | 記録が「作業」でなく「蓄積」になる。1行だから続く |
| 遊びネタカード | 「何して遊ぶ？」の判断疲れを消す |
| mood 記録 | しんどさの兆候を早期発見し、燃え尽きる前に減らす |
| 自己ベスト表示 | 比較対象が過去の自分だけなので健全に効く |

### 16.2 アンチパターン

| ❌ | なぜダメか |
|----|-----------|
| 妻のタスクを記録し始める | 監視になる。関係が壊れる。原則1違反 |
| 週報を妻に見せて「これだけやった」と言う | 承認を求める行為が相手の負担になる。数字は自分のためだけ |
| 全機能を作ってから運用開始 | 8割は完成前に飽きる。Phase 0 は手動で回す |
| 未完了に追撃リマインド | 通知が敵になる。1回出したら黙る |
| タスクを細かく割りすぎる | 「Issue を閉じる作業」が新しい家事になる。1日8件が上限目安 |
| 記録の完璧を目指す | 記録漏れは前提。漏れても崩れない集計にする |
| 目標を上方修正し続ける | 上限は §6.2 の見積もり。超えて走り続けると燃え尽きる |

## 18. 非機能要件

### 18.1 プライバシー
- **Private リポジトリ必須**。子の生年月日・生活リズム・在宅パターンが含まれる。
- 子の氏名・写真・位置情報はコミットしない。ニックネームのみ。
- Webhook URL は GitHub Secrets に格納。ハードコード禁止。

### 18.2 運用コスト
- Actions 実行は 1日 6〜8回 × 各1分未満 → 月 200〜300分程度。Free プラン（Private 2,000分/月）の範囲内。
- 生成物のコミットは `[skip ci]` を付与し、ワークフローのループを防ぐ。

### 18.3 可用性・フォールバック
- Actions が落ちても**手動で Issue を作れば全機能が回る**こと。Bot は「便利さ」のみを提供する。
- 集計はログから再計算可能（冪等）。ログが壊れたら Issue 履歴から再生成できる。

### 18.4 保守性
- Routine の追加は YAML 1ブロックで完結（コード変更を伴わない）。
- ナレッジの追加は Markdown 1ファイルで完結。
